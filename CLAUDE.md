# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

Telegram bot (aiogram 3, Python, SQLite via aiosqlite). Tests use pytest; no linter or build step is configured.

```bash
python -m venv venv && source venv/bin/activate   # venv/ is gitignored
pip install -r requirements.txt
cp .env.example .env                              # then fill in values
python main.py                                    # long polling; creates bot.db on first run
pip install -r requirements-dev.txt && pytest     # tests/: no network, no real .env values, temp SQLite per test
```

Tests: `tests/conftest.py` sets every env var before `config` is imported (so `.env` secrets never reach tests), `tests/telegram_fakes.py` is a recording fake Bot API session plus Update builders, `tests/flow.py` feeds updates through the real routers (`Dispatcher.feed_raw_update`). Known bugs are pinned as `xfail(strict=True)` with a `BUG:` reason: when one is fixed its test XPASSes and fails the run, so remove the marker then.

Webhook (optional): set `WEBHOOK_URL` (public https base URL), `WEBHOOK_SECRET` (16+ chars, `openssl rand -hex 32`), optionally `WEBHOOK_PATH` (default /webhook), `WEB_HOST`, `WEB_PORT` (8080) in `.env`; `main.py` then serves `/webhook` (checked against the secret token) and `/health` over plain HTTP via aiohttp, calls `set_webhook` on start, and expects a reverse proxy to terminate TLS and forward to the port; without `WEBHOOK_URL` the bot uses long polling (which removes any old webhook). Everything else (expiry loop, delete queue, commands) is identical in both modes.

Docker: `docker compose up -d --build` runs the bot; `bot.db` lives in the `bot-data` volume (`DATA_DIR=/data`, default `.` locally).

Env vars (read in `config.py`): `BOT_TOKEN`, `ADMIN_IDS` (comma-separated Telegram IDs of the bot admins; there is ONE role, "admin", and it is defined only by this list, never by Telegram group admin/creator status; admins must press /start in the bot once; empty list = nobody can review or run commands), `DEVELOPER_IDS` (optional, comma-separated: uncaught handler errors are logged and DMed to these developers with update/chat/user context by `handlers/errors.py`, never to admins), `VOTING_MINUTES` (1 to 10080) (default 10: voting window in minutes), `API_URL` (AI xizmatining to'liq endpoint URL'i, faqat https; localhost uchun http mumkin), `API_TOKEN` (Bearer token), `API_MODEL` (default `chat/answer`). `VOTE_ACCEPT_PERCENT` (default 60, 1 to 100: share of 👍 among all votes that accepts the applicant), `AUTO_DELETE_SECONDS` (default 30, 0 disables: `utils/autodelete.AutoDeleteMiddleware`, a session request middleware, deletes every message the bot sends into a group after that delay, except AI answers (sent inside `keep_messages()` in `handlers/ai.py`, so users can keep replying to them) and the vote message (`VoteCB` buttons), which `utils/voting` removes when voting ends; also `CommandCleanupMiddleware` deletes the admin's own handled command message (/finish, /ban...) after the same delay; the queue lives in the `pending_deletes` table and `restore_pending_deletes` resumes it at startup, so restarts do not leave messages behind; a failed delete (e.g. the bot lacks the delete-messages right) is logged as a warning). Logging: `utils/logging_setup.py` (console + rotating `DATA_DIR/logs/bot.log`, 5 MB x 4 files = at most 20 MB, level via optional `LOG_LEVEL`; docker-compose also caps the stdout logs at 3 x 10 MB; plain group chatter is logged only at DEBUG and the duplicate `aiogram.event` lines are muted so production logs stay small); `utils/request_log.py` logs every incoming update (`tg.in`, free-text answers only by length — they are personal data) and every Telegram API call/response (`tg.out`, `GetUpdates` only at DEBUG). There is deliberately no group ID in config: the bot is deployed into whatever group it is added to, and the group is always taken from the update (join request chat, `my_chat_member`, message chat).

## Architecture

The bot gates entry to a Telegram group: a user who requests to join fills in a questionnaire (anketa) in a private chat, the admins (`ADMIN_IDS`) approve/reject it, and approved applications go to a group-wide vote.

Flow across files (it spans several, so read them together):

1. `handlers/join.py` — `chat_join_request` handler. Greets the user via DM and sets FSM state `Form.age` **for the private chat** using `utils/fsm.get_private_state` (the update comes from the group context, so the state key must be built manually). It stores `group_id` in FSM data so later steps know which group the application is for. If the user already filled in an anketa before (`database.get_profile`, table `profiles`, keyed by user_id; `save_profile` is an upsert), the questions are skipped: the bot shows the saved anketa (`Form.review`, `handlers/profile.py`) with "O'zgartirish" / "Shunday qoldirish" as plain reply-keyboard buttons (two rows; `keyboards/profile.py`, matched by text, no callbacks). "Shunday qoldirish" → `utils/applications.apply_from_profile` creates the application and starts the group vote directly (`open_voting`, shared with `handlers/admin.py:accept`), without a new admin review. "O'zgartirish" → field menu (`Form.pick_field`, reply keyboard) → the normal question for that field is asked with FSM flag `editing=True` (`anketa._advance` then calls `profile.finish_edit` instead of moving on), the profile is saved and the review is shown again. If the user's latest application in this group is `rejected` (by an admin, by vote, or by an admin's final decision), the saved profile is NOT shown or reused: they get `REJOIN_AFTER_REJECTION` and the questionnaire starts from scratch (`database.last_application_status`); other statuses (expired, failed) still show the saved profile.
2. `handlers/anketa.py` — private-chat FSM steps (`states.Form`: full_name → phone (optional) → age → job → about → join_group; question texts/keyboards live in `utils/questions.py`, the optional phone has a skip button; the Telegram username is NOT asked: it is taken from the Telegram profile at join time / on completion, stored in `applications.tg_username` and the saved profile, and never shown in any anketa text; name and surname are asked in ONE question (`full_name`, at least two words; old saved profiles with separate first_name/last_name still work via `utils.form_anketa.full_name_of`); the phone is shown only to admins, never in the group's vote message). On the last step it formats the anketa, inserts an `applications` row, and DMs every non-bot group admin with `keyboards/action.py` inline buttons (`ApplicantCB`). On the last step the answers are also saved once with `save_profile` (`INSERT OR IGNORE`, fields in `utils/form_anketa.PROFILE_FIELDS`).
3. `handlers/admin.py` — `accept`/`reject` callbacks. Verifies the clicker is in `ADMIN_IDS` (`utils.admin.is_admin`), then transitions status atomically with `database.change_status(old, new)` (`UPDATE ... WHERE status = old`, so double-clicks are rejected). `reject` declines the join request; `accept` moves to `voting` and posts a vote message with `keyboards/vote.py` (`VoteCB`) into the group, saving `vote_message_id`.
4. `handlers/vote.py` — `on_vote` records one vote per group member (`votes` table, applicant can't vote on own application); every vote counts as 1, admins included. Tallies are deliberately never shown in the group (buttons carry no counters). A vote button pressed on a stale message (unknown/finished application, or a message that is not the application's `vote_message_id`, e.g. after a DB reset) is refused and that message is deleted. It never finalizes: `accept` in `handlers/admin.py` calls `database.start_voting` which sets `applications.voting_ends_at` (now + `VOTING_MINUTES` minutes), and `utils/voting.finalize_due_votings` (applications are finalized concurrently; the AI-written rejection note is computed last and every AI call is capped at 10 s with a plain-text fallback, so group-side work never waits for the AI) (called every 15 s from the loop in `utils/expiry.py`, so an expired vote message disappears within seconds, no /finish needed; also at startup) closes due votings: no votes → `expired`; 👍 ≥ `VOTE_ACCEPT_PERCENT` % (default 60) of all votes AND more 👍 than 👎 → `accepted` automatically (the majority condition only matters for percent ≤ 50); 👎 ≥ that % AND more 👎 than 👍 → `rejected` automatically; if neither side reaches it → status `creator_review`: the join request stays pending and the report (`utils/voting._send_to_admins`, just the anketa + phone, no title, counts, percentages or reasons) goes with Qabul/Rad buttons to every `ADMIN_IDS` admin, and `handlers/creator.py` (`CreatorCB`) lets any admin decide (first wins, `change_status` is atomic); the confirm view is ALWAYS shown: Qabul → AI summary of the 👎 reasons (`utils/summary.summarize_reasons`) + "Ha, qabul qilaman"; Rad → 👍 count + "Ishonchingiz komilmi?" + "Ha, rad etaman"; both have "Orqaga"; if no admin can be DMed the majority decides. Every rejection (auto or admin) DMs the applicant a soft AI-written general explanation of the 👎 reasons (`utils/voting.rejection_note` → `utils/summary.feedback_for_applicant`: never exact reasons, names or counts; no reasons or AI failure → plain rejection text). every final outcome (auto accept/reject, expired, or an admin's decision, the latter only to the *other* admins with "(qaror: name)") is announced to the admins as a short status DM via `utils.admin.notify_admins`/`status_text`: «Ism Familiya guruhga qabul qilindi / qilinmadi»; the vote message is deleted (edited with the result if deletion fails) and the applicant is told the result.

Anti-advertising in the group (`handlers/ads.py` + `utils/ads.py`, router registered before the AI router, filter-based so non-ads keep flowing to other handlers; also handles edited messages and photo captions): a non-admin's message is deleted at once if it has a Telegram link (t.me, telegram.me, tg://, also in text_link entities) or is forwarded from a channel; messages with another URL/domain, a phone number or a promo keyword are sent to the AI (`AD`/`OK`, 6 s cap, fail-open) and deleted on `AD`; plain chat never costs an API call. Exempt: `ADMIN_IDS`, Telegram group admins/creator (checked only for flagged messages), anonymous-admin posts, the linked channel's auto-forwards, bots. A short warning (`AD_NOTICE`, at most once a minute per user) is posted and auto-deletes. The bot needs the delete-messages right.
Moderation: every free-text answer (full name, job, about, join reason, edits) and every 👎 reason goes through `utils/moderation.is_abusive` (first a fast local filter `utils/profanity.has_profanity`: normalised Uzbek/Russian/English obscenity roots, Cyrillic/leet/repeats/spelled-out letters, deliberately conservative so words like "sikl" or "harom" are fine; then the AI, `max_tokens=10`, 6 s cap, answer matched as the word BAD; the local filter works even when the AI is down): profanity/insults/obscene/hate/threat text is refused with `MODERATION_WARNING` and must be rewritten (state does not advance, nothing is stored); phone and age are not sent to the AI; if the AI is down or slow the text is let through (fail-open); the user text is wrapped in `<<< >>>` and declared untrusted data in the system prompt.
5. `handlers/reason.py` — a 👎 vote makes the bot DM the voter asking for a reason; admins (`ADMIN_IDS`) get the same question plus a reply-keyboard "o'tkazib yuborish" button (skip stores an empty reason: not asked again, ignored by the AI summaries; typing a reason stores it normally) (if the DM fails, the voter is told to `/start` the bot and `handlers/start.py` re-asks). The reply is matched to the voter's latest reason-less 👎 vote from the last 24h (`database.get_pending_reason`, no FSM). Reasons are only stored (`votes.reason`); they are used once, when a rejected voting is finalized (see 4). Once voting has ended no reason is asked or accepted (`get_pending_reason` requires a live voting window).

6. `handlers/group.py` — group moderation commands (`/kick_deleted`, `/ban`, `/unban`, `/mute`, `/unmute`, `/stats`, `/finish` — must be sent as a reply to a vote message; ends only that application's voting via `database.end_voting_now` + `utils/voting.finalize_due_votings`, replies only with a short "🏁 Ovoz berish yakunlandi." in the group (auto-deleted; no DM summary); without a reply it finishes nothing). A router-level `admin_only` filter (`ADMIN_IDS`, no Telegram API call) means only admins are obeyed; /ban and /mute also refuse to touch `ADMIN_IDS` and Telegram group admins; the "/" menu is set per admin via `utils/commands.setup_group_commands`; everyone else gets no reply, but their typed command message (only our own commands, not other bots' `/...`) is auto-deleted after `AUTO_DELETE_SECONDS` by the second router `group.strangers`. The Bot API cannot list group members, so `/kick_deleted` only checks members the bot has *seen*: `utils/members.TrackMembersMiddleware` (all group messages, join/leave service messages) and the `chat_member` handler record them in the `members` table. The command re-fetches each tracked member and kicks (ban + unban) those whose first name is "Deleted Account". Old silent members the bot never saw are not covered — an earlier Telethon userbot approach was dropped on purpose (personal-account session risk).

7. `handlers/ai.py` + `utils/ai.py` — AI assistant in groups. A message that mentions the bot (`@bot ...`) or replies to one of the bot's earlier AI answers is sent to an OpenAI-format `chat/completions` API (`ask_ai`, aiohttp, `API_URL` is the full endpoint, https only (http allowed for localhost); `max_tokens` capped, Bearer `API_TOKEN`) and the answer is sent back as a reply (Telegram HTML; if Telegram rejects the markup it is resent as plain text; split at 4096 chars; the HTTP session is shared (keep-alive, `utils.ai._get_session`, closed in `main.py`) and `max_tokens` is 900 to keep answers fast; `utils/ai_html.sanitize_html` is an allowlist sanitizer: only b/i/u/s/code/pre and `<a>` with an https href survive, everything else is escaped, tags are balanced, and hyphens/dashes outside URLs and code become spaces or `•` — model output is untrusted (prompt injection), never send it unsanitized). Conversation memory is only the replied-to AI answer (Telegram gives one reply level); AI answer ids are kept in memory (`_ai_messages`, lost on restart). Per-user 5s cooldown; answers capped (`max_tokens`, 2 messages). `AIError` replies with a generic message, then re-raises so `handlers/errors.py` DMs the developers. Never log `API_TOKEN`.



Application status lifecycle: `pending` → `rejected` | `voting` → `accepted` | `rejected` | `expired` (voting deadline passed with zero votes). Admins review the anketa (`pending`); a vote result that misses the threshold on both sides goes to the admins (`creator_review`, name is historical: there is no creator role). Applications still `pending` 3 days after creation, or `creator_review` 3 days after voting ended, become `expired` (`utils/expiry.py`, background loop started in `main.py`, runs every 15s: declines the join request, closes the vote message, notifies the applicant), so the duplicate-application guard cannot block a user forever.

Supporting pieces:
- `handlers/__init__.py:get_routers()` — router registration order matters; add new routers there.
- `callbacks.py` — `CallbackData` factories; `texts.py` — user-facing message constants; `utils/` — bot instance (`create_bot.py`), `safe_send`/`is_group_admin`/`mark_done` helpers (`admin.py`), typing-delay sender, number extraction, anketa formatting.
- `database.py` — every function opens its own `aiosqlite.connect(DB_PATH)` connection (`bot.db` in the cwd, gitignored via `*.db`); FSM state/data also live in `bot.db` (`fsm` table, `utils/fsm_storage.SQLiteStorage`) so half-filled anketas survive restarts; schema is created by `init_db()` with `CREATE TABLE IF NOT EXISTS`, so schema changes need a manual migration.
- All user-facing text is in Uzbek; keep new messages and log strings consistent with that.
